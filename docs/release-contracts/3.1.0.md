# V3.1.0 Release Contract

## Decision

採用済みDecide014のRelease Goal・Scope・AC・Release Contractを転記した実装契約です。QA最終回答と親#672・子#673〜#679/#686〜#689、Milestone105へ対応し、実装・検証・正式公開の証拠で完了判定します。下記チェックは必須証拠の確認前に完了扱いへ変更しません。状態の正本は[GitHub Release](https://github.com/Tao-pyth/master-duel-recorder-lite/releases/tag/v3.1.0)、[親Issue #672](https://github.com/Tao-pyth/master-duel-recorder-lite/issues/672)と対応するAct記録です。

採用文書のNon-Scope末尾にある「今回変更しない」は、Decideでの計画登録時点の境界です。ActではRelease Contractのrequired項目であるコード・検証・版数・正式公開を扱います。実運用データ・資格情報は試験・編集対象にしません。ローカル・公開配布の証拠は[検証記録](../validation/3.1.0.md)で区別します。

## Release Goal

元動画を整理しながら、録画非依存の対戦カード情報・初動・URLを長期に蓄積し、JSON/削除/復元/終了/再試行を一貫させる。

## Target Version

baseline v3.0.0、target_version v3.1.0。採用時点でbaselineのソース/正式Release/tag/文書を照合した。DB target19（W8の単一統合移行）、AppConfig欠落既定値のみ。

## Scope

1. 保存容量は非負整数GiB（1GiB=1,073,741,824bytes）、保存期限は非負整数日。0=無制限、旧/新設定は0。AppConfig.recording_storage_max_gib/recording_retention_days、[storage].max_gib/retention_days。投稿後boolは初期false、[upload].delete_source_after_upload。欠落既定値のみ、自動書換なし。
2. 対象はRuntimePaths.recordingsの元動画。exports内MP4/clip、preroll、未登録動画を自動削除しない。未登録/保護等も実ファイル総容量へ算入し、未達の理由を表示する。
3. 通常GUI起動で移行/初期化→未完了journal回復→期限→容量→明示投稿後再試行要求→worker/操作解禁。constructor・参照/診断CLI・worker・version/smoke・設定保存・復元だけでは新規整理しない。
4. 期限はUTC録画開始時刻（欠落created_at）、固定nowとのage>retention_days×86400。ちょうど期限は保持。古順は基準時刻とrecording_id、mtimeを使わない。容量は期限処理後に実サイズを再評価し<=上限で止める。全件走査でGUI1000件制限へ依存しない。
5. 登録済み正常完了/確定terminal失敗の安全な元動画のみ。保護/実行中録画・準備/原動画使用中/復旧対象/未知日時/境界外・外向きリンク・共有参照・変化ファイルを除外。対象外を消して上限を達成しない。
6. 対戦カード正本はduel_id・安定カードID・使用者、使用/明示非使用/不明、確認経緯/revision、初動で完結。recording/marker/job/動画時刻を必須依存にしない。カード設定無効化で過去正本を消さない。
7. 動画観測/時刻/候補/一般・カードマーカー/解析入力は動画実体と時刻基準に所属し、正本への根拠は0〜複数。明示確認でだけ意味情報へ反映。再解析は未レビュー候補の更新まで、人の使用/非使用/初動を上書きしない。
8. 元動画削除成功時、対象の一般/カードマーカー・未確認候補を削除。戦績/タグ/メモ/対戦カード正本/非使用/初動/投稿URL/MP4/clipを保持。確認済み集計は不変、候補参考は減り得る。候補0やマーカー不在を非使用にしない。
9. 事前DB/config backupは検証だけでなく削除処理中の実在を保証。世代/容量枯渇等で保持できなければ削除0件。intent先commit→同volume限定staging→staged保存→unlink→完了DB commit。unlink成功前にマーカーを不可逆に消さない。
10. rename/unlink/DB失敗を正常完了にせず、unlink前は復元/中止、unlink後はjournalから状態・理由を回復。動画backupは作らず、unlink後の動画復元は保証しない。既存理由を重複処理で上書きしない。
11. GUI/既存CLI単件/待機投稿の共通serviceで、API受領成功かつCOMPLETED/video_id/watch_urlのDB保存・再読込後に最新saved boolを確認。投稿開始時/未保存checkboxでは判断しない。送信成功とYouTube処理/再生完了は別で、処理完了ポーリングは追加しない。
12. 実際に投稿したMP4/manifestのsource/export path/size/SHA、recording/queue/prepare参照を現DB/元動画へ照合。OFF/読込失敗/不正値/非completed/結果未保存/保護/使用中/出自不一致では削除しない。破壊操作前にも最新値/保護/現物を再確認する。
13. 投稿後削除理由はyoutube_uploaded（YouTubeアップロード完了後）。成功URL・投稿stateは削除失敗/台帳失敗と別に維持する。ONで適格な一時的見送りを行った投稿だけ、理由・出自付き再試行要求を永続化して次回通常GUI起動へ渡す。
14. 再試行は保存された要求だけを対象にし、最新saved設定・保護・使用中・出自・backupを再検証する。OFF/保護等では削除しない。既削除は旧理由を維持して不要/完了。要求のない過去completedを遡及一括処理せず、intent/要求前のクラッシュでは元動画保持。
15. 投稿中の終了操作は投稿・削除後処理が成功/見送り/失敗の終端になるまで待つ。GUIイベントと表示を維持し新規操作を抑止。削除失敗を投稿失敗や無期限終了待機へ変換しない。旧closing後の新規削除見送り案は撤回。
16. 画面に『動画だけ削除』と『戦績・録画履歴ごと削除』を別操作/確認文で用意。保護対象の手動削除は追加警告、キャンセルでDB/動画不変。手動は追加警告への明示継続時だけ保護対象の削除を許可し、保護フラグ自体は解除しない。自動整理/再試行からこの許可を使わない。動画のみ削除は共通サービスを使う。
17. JSONは正本/非使用/初動/必要カードID・完了YouTube URL/video_id・カード/一般マーカーと動画同一性・確定削除理由日時・保護をportable対象にする。動画なしでも意味情報は往復。マーカーは内容/時刻基準一致まで利用不可。
18. JSONにはOAuth・動画ファイル/MP4・送信待ち・解析job/checkpoint・未完了削除intent・投稿後再試行要求を含めず、禁止table/stateを拒否。取込された完了投稿/確定削除履歴から実行要求を生成しない。旧JSON欠落は未登録/既定値とし、非使用/完了/原因を推定しない。
19. 完全削除/手入力対戦削除/history/all reset/JSON全置換は所有者別に関連情報を子→親へtransactionで処理。共通カードと他対戦は巻き込まない。自由記述tag resetはタグ風の対戦カード情報を消さない。リモートYouTubeは削除しない。
20. 管理操作/復元/保存先変更/再関連付けは共有排他・事前backup・未完了journal gateを通す。現地pendingがあれば拒否して通常起動回復へ案内。restore由来journal/job/markerは現物一致まで実行・利用不可。復元自体は新規整理契機にしない。
21. 復元成功時だけ設定値/保護表示/dirty基準を再読込。snapshot内の情報だけを使い後発の削除理由を引き継がない。復元時に確認できる削除状態は『復元時削除済み』、元の原因不明は別保持。未接続/権限不足等は『確認不可』。
22. schema19のDDLと17/18→19のprotected単一移行はW8に一本化。confirmed表示だけを使用へ変換せず、supports_use/action/actor/cardと独立した非使用/初動を保持。未対応は要確認で元情報を残す。
23. 確認済み使用/明示非使用/初動を持つ録画に戦績がなければdraft戦績を1件自動作成。開始日時（欠落created_at）、勝敗/先後/コインはunknown、デッキ/メモを捏造しない。候補だけから作成・確定しない。再実行で増殖しない。
24. 動画なしでも一覧から対戦カードを閲覧/付与/訂正・初動/勝敗統計・URLを利用可能にする。有効な準備済みMP4の初回投稿/再試行を維持し、元動画必須の再生/seek/再解析/新規準備だけを制御する。
25. F1の古い動画への検索/一覧/ページ移動拡張と専用GUI試験は不採用。既存画面での保護と全件/1001件以上の整理試験は維持。容量逼迫時の空き確保→再起動、見送り/再試行待ちの手順を説明する。

## Non-Scope

exports/clip/preroll/未登録の自動削除、常時整理、全過去completed遡及処理、動画backup/復元、新OAuth/送信取消/処理完了待ち、全カード辞書/精度改善/複数動画/独立入力省力化、F1一覧拡張、専用整理CLI/新GUI再投稿/単件再試行UI。実データ・source/test/version/CI/Releaseを今回変更しない。

## Chosen Approach

DBDDLとprotected17/18→19移行を新W8へ一本化し既存W1はデータAPIへ絞る。新W9を正本API/画面/統計、W10をportable形式/ID対応/取込計画/隔離材料化、W11を既存DB置換/関連削除/管理gate/復元同期とする。既存W3〜W7へQAを補足し、W6が全契約を証拠付きで完了する。

## Acceptance Criteria

- [ ] AC1 旧/新設定は容量/期限0・投稿後false、GUI/CLI保存と再読込が一致。不正値/未保存/読込失敗で削除しない。
- [ ] AC2 全件の期限境界・容量境界・安定古順・実サイズ・未登録/保護容量を扱い、未達理由を表示する。1001件以上でも正しい。
- [ ] AC3 全自動入口で保護/使用中/復旧/境界外/変化した別動画を削除せず、事前backupの保持不能は削除0件。
- [ ] AC4 正本・非使用・初動が動画/marker/jobなしで成立。削除/再解析/差替え/対象設定変更で確認済み集計を変えない。
- [ ] AC5 元動画削除成功時に動画依存マーカー/候補を除去し、物理削除失敗では不可逆に失わない。候補参考の変化を非使用にしない。
- [ ] AC6 全intent/staging/unlink/DB障害境界で二重削除・正本消失・理由捏造・別動画誤削除がなく、冪等回復する。
- [ ] AC7 投稿成功保存後に最新saved ONと出自を判定し、GUI/CLI全投稿入口で成功URLと削除結果を分離する。
- [ ] AC8 適格見送りの永続要求だけを翌GUI起動で再試行。最新OFF/保護/使用中/不一致/backup失敗で保持。旧completedやJSON取込から要求を生成しない。
- [ ] AC9 終了操作は投稿/後処理の終端まで待ち、GUI非freeze・成功/失敗/見送り後に終了できる。失敗を無期限待機にしない。
- [ ] AC10 動画のみ/履歴全削除を別操作にし、保護警告・取消不変・選択範囲の処理が成立する。
- [ ] AC11 新JSONで正本/初動/URL・video_id/マーカー/確定理由日時・保護を往復し、旧JSON互換と禁止実行データ拒否を示す。
- [ ] AC12 既存DBへの取込・完全削除・各初期化・手入力削除でFK/孤児/部分commitがなく、共有情報・他対戦・リモート投稿を巻き込まない。
- [ ] AC13 復元成功時だけ設定/保護/編集基準が一致。復元から新規整理しない。『復元時削除済み』と原因不明/確認不可を区別し、後発理由を捏造/引継ぎしない。
- [ ] AC14 schema17/18→19のbackup/rollbackとdraft救済・未対応要確認が成立し、移行前後の確定情報/集計が一致、再実行で増殖しない。
- [ ] AC15 動画なし手入力/取込カード編集・統計・URL・有効MP4投稿を製品入口で確認し、原動画必須操作だけ不可とする。
- [ ] AC16 別process・原動画利用・管理操作・遅い解析結果が交差しても誤削除や候補復活がない。
- [ ] AC17 重点/全unittest(ResourceWarning error)・Ruff・実Qt・WindowsGUI100/150/200%と小画面・既存OCR回帰・3EXE/7assets検証が成功。
- [ ] AC18 Actで2version/main/tag/正式Release/文書を3.1.0へ揃え、required証拠と公開再取得検証後に本版対象だけcloseする。

## Rejected Alternatives

closing後削除見送り、timeline/候補一律保持、対戦の正本/初動/通常統計がmarkerへ依存、復元前理由のsnapshot引継ぎ、JSON active処理再生、全旧completed自動削除、保護を消して上限達成、F1拡張を採らない。

## Risks

unlink後の動画復元を保証しない。snapshot後の正本・理由が戻ると保証しない。確認不能と削除済みの表示を分ける。設定/保護/出自/backup保持/共有排他を破壊操作直前に再確認。draft救済・未対応情報を黙って捏造/破棄しない。

## Deferred Solution Queue Intake

全カード抽出、連続レビュー作業位置、タグ補完、独立入力省力化などKeep。Queue更新なし。F1はRejectのまま。別V3.2.0 #680〜#685と独立#629は変更しない。
