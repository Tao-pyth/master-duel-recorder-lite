# V3.1.0 管理操作とバックアップ復元の境界

## 管理操作の排他

JSON全置換・各初期化・履歴完全削除・復元など、所有者を変更する操作は `video_management_gate(paths, database_path=...)` を最外周で一度だけ保持する。`video-operations.lock`、`recording.lock` の順に取得し、事前バックアップから変更の完了まで解放しない。

削除サービスの同一インスタンスで既に両排他を保持する履歴完全削除は、再取得せず `assert_video_management_allowed()` で同じ状態検査を行う。この関数だけを排他なしで管理変更の許可に使わない。

次の状態があれば管理変更を拒否する。

- 未完了の動画削除journal（intent / staged / unlinked）：通常GUI起動の回復へ案内する。
- 全動画世代の利用lease：生存PIDと終了確認不能のPIDを保持する。確実な終了PIDだけを排他の下で除去できる。
- 実行中カード解析、準備中・送信中YouTube投稿、処理中のMP4準備キュー。

schema17/18以前に新しい管理tableがないことは正常として扱う。検査できないDB・キューを「利用なし」と判断しない。プレビュー・診断は読み取り専用で、管理gateを必要としない。

## 復元候補の検証と移行

復元は現地の管理gate、直前の保護バックアップ、別パスへの候補展開、memberのサイズ・SHA・SQLite整合性・設定検証、候補内移行、配置、配置後検証の順に進める。旧17/18の候補は、候補自体の旧版DB・設定を `pre-restore-migration-vN` の保護世代として残した後、単一移行で19へ変換する。現在のDBを一度旧版へ置き換えてから移行しない。

途中失敗では現DB・設定を退避材料へ戻す。退避復帰自体が失敗した場合は「戻しました」と報告せず、退避DB・設定と保護世代を保持して不成立を伝える。録画、MP4、キュー、資格情報を復元対象に増やさない。

## 復元由来の実行・根拠情報

- 対戦カード正本、初動、タグ・メモ、完了投稿URL、保護とsnapshot内の確定削除履歴を保持する。
- 非削除動画実体を未検証とし、解析入力・一般マーカー・カード観測の `verified` を0へ戻す。ファイルの有無だけで古い時刻・根拠を利用可能にしない。
- snapshot内の利用leaseは現在のprocessの権限ではないので除去する。実processを終了させる操作は行わない。
- running解析を入力確認待ちへ、preparing/uploading投稿を失敗・状況確認へ移す。投稿先の重複を避けるため、再投稿前のYouTube Studio確認を案内する。completedとURLは変更しない。
- 未完了削除journalに `restored_from_backup` を記録する。復元操作では実行せず、次の通常起動で現物、最新設定、保護、出自、バックアップを再検証する。復元snapshotのstagedで原動画・退避動画が両方ないだけなら、旧原因でunlink成功を推定しない。
- 投稿後再試行要求も復元直後には消費しない。次の通常起動の保存要求のみの再試行に委ねる。取込された完了投稿から新要求を作らない。

## 動画が見つからない場合

保存先へ到達でき、snapshotが指す現在の動画の不在を確認できた場合は `restored_deleted`、`cause_known=false` として「復元時削除済み」を表示する。日時は復元時の確認日時であり、実際の削除時刻を捏造しない。元の削除時刻が不明なことをmetadataへ残す。snapshotの確定削除原因・日時がある場合はその情報を保持し、復元前の後発原因をコピーしない。

保存先の未接続、権限不足、境界外・リンクなどで実体を確認できない場合は「確認不可」とし、削除済みに変換しない。未完了journalの動画を復元だけで削除完了に変換しない。復元で動画本体は戻らない。

GUIは復元成功時だけ設定・保護・未保存編集の基準を読み直す。失敗した復元で画面の編集内容を失わせず、復元操作から新しい容量・期限・投稿後整理を開始しない。
