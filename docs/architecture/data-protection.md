# データ保全設計

## 保護対象と除外対象

バックアップはSQLite履歴DBと存在する場合の`config/app.toml`を保護します。V3.1.0のschema19では、戦績、録画履歴、管理カタログ、保存済みフィルター、対戦カード正本・初動、動画マーカー・削除監査・未完了journal・投稿後要求も同じDB snapshotへ含みます。録画、MP4、診断ログ、画面画像、準備キュー、OAuth情報や秘密情報は含めません。動画本体を削除した後にDBを復元しても動画は戻りません。

バックアップは`user_data/data/backups/*.mdrl-backup`へ保存するZIPです。許可memberは`manifest.json`、`data/history.sqlite3`、任意の`config/app.toml`だけです。manifestには形式版、作成日時、作成契機、保護状態、DBスキーマ版、管理データ件数、各memberのサイズとSHA-256を記録します。絶対パスと秘密情報は記録しません。

## 作成と保持

SQLite Backup APIで稼働DBから一貫したスナップショットを別ファイルへ作成し、`quick_check`、`foreign_key_check`、スキーマ版、件数を検証してからZIP化します。一時ZIPを同一ディレクトリで完成させ、最後に原子的置換します。検証・権限・容量・置換のいずれかが失敗した場合は一時物を削除し、未完成世代を公開しません。

次の操作前に用途名付きバックアップを作成します。

- DBスキーマ移行: `pre-migration-vN`。公開済み旧スキーマを復元できるよう保護世代とする
- 管理データ取込・初期化: 既存の操作前バックアップを検証済み形式へ統一する
- 復元: `pre-restore`。復元直前の状態を保護世代とする
- 録画再関連付け、戦績・録画履歴削除: 操作前の通常世代を作成する
- 容量・期限・投稿後・手動の動画のみ削除: 処理が終わるまで通常世代を必須保持する
- 利用者操作: `manual`

保持枠は最大20世代、合計256MiBで、保護世代も件数・容量へ算入します。保護世代は自動削除せず、残りの枠へ新しい通常世代から保持します。ローテーションはバックアップディレクトリ直下の検証済み通常世代だけを削除します。保護世代は移行・復元の基準点で、通常操作のたびには作りません。

`retained_backup`はOS共有排他を保持し、削除処理に必要な通常世代を処理終了まで必須保持します。保護世代で枠が埋まる場合、新しい通常世代が容量枠に入らない場合、作成・検証・保持に失敗する場合は削除を開始しません。破壊直前にも実在とSHAを確認します。先に別データを片付けて空きを確保し、必要なバックアップを別の場所へ保管して保持枠を見直してから通常GUIを再起動する手順を[操作説明](../releases/3.1.0.md)へ記載します。

## 復元

復元候補は現DBと別の一時パスへ展開し、許可member、サイズ、SHA-256、SQLite整合性、外部キー、スキーマ版を検証します。現在版より新しいDBは拒否します。GUIは現在と候補の録画履歴、戦績、デッキ、タグ、シーズン、保存済みフィルター件数と設定の有無を提示し、確認後だけ復元します。

復元は共通管理gateで動画操作・録画を隔離し、現在の未完了削除・利用中・実行中処理があれば拒否します。事前保護バックアップを作り、旧候補DBを別パスで保護移行してschema19へ揃え、現DB・設定の退避、候補配置、再検証へ進みます。配置後の検証を含む途中失敗では退避DBと設定を戻します。復元前に設定がなかった場合は失敗中に配置した設定も除去します。rollback自体の失敗も隠さず、退避材料を保持して案内します。

復元成功時だけGUIの保存済み設定・保護表示・未保存編集の基準を同期します。復元自体から新しい容量・期限・投稿後整理を開始しません。snapshot内の解析入力・マーカーを未検証へ戻し、古いprocessの利用leaseを実行権限として再利用しません。途中の解析は待機、途中の投稿はリモート重複を避ける要確認状態へ戻し、成功済みURLを保持します。snapshot由来journal・再試行要求は次の通常GUI起動で最新設定・保護・現物・出自を確認するまで実行しません。

復元では動画本体を書き換え・移動・削除せず、保存先と現物の状態だけを確認します。snapshotにある確定削除理由・日時は保持します。snapshotにない後発理由は引き継がず、保存先を確認できて動画が不在の場合は「復元時削除済み」、元原因不明として記録します。その日時は復元時確認日時です。保存先未接続・権限不足は「確認不可」とし、不在や削除成功を断定しません。[詳細](retention-management-3.1.0.md)を参照してください。

## 読み取り専用診断

統合診断は設定妥当性、`quick_check`、`foreign_key_check`、管理データ件数、録画参照の保存先逸脱・欠損・サイズ不一致、未登録mkv/mp4に加え、確定削除・復元時削除済み・確認不可・未完了削除・投稿後再試行待ちを区別します。診断はDB・設定・録画を変更せず、自動修復・新しい整理・自動統合を行いません。

欠損録画は録画保存先配下の既存mkv/mp4だけを候補にでき、空ファイル、別履歴が使用中のパス、保存先外を拒否します。確認時のサイズとSHA-256を再実行時にも照合し、変化がなければDBの相対参照とサイズだけを更新します。動画自体は変更しません。

## 重複候補

重複候補は開始時刻差、勝敗、先後、自分デッキ、対戦種別、録画サイズ・SHA-256から点数化します。録画なしの対戦は強いメタデータ一致、録画ありの対戦は録画一致または十分なメタデータ一致が必要です。GUIは2件の日時、録画ID、デッキ、勝敗、先後、タグ、メモと根拠を並べます。両方保持、個別編集、片方削除だけを提供し、自動マージしません。削除前は管理データバックアップと確認を必須にし、録画付き戦績の削除では動画も削除されることを明示します。
