# 録画履歴

## 目的

V0.5.0では録画の開始から完了または失敗までをSQLiteへ保存し、後から結果と失敗理由を確認できるようにします。DBは `user_data/data/db/history.sqlite3` に限定し、録画ファイルそのものとは分離します。

## スキーマと状態

`schema_version` は単一の整数版を持ち、現在の版は8です。`recordings` は録画IDを主キーとし、出力相対パスにも一意制約を持ちます。版7では旧復旧テーブルと専用列を撤去し、失敗コードと診断は維持します。版8ではシーズン、対戦記録の自分・相手デッキID、デッキカラー・用途フラグを追加します。

```text
starting -> recording -> completed
                      -> failed
starting ----------------> failed
```

各履歴は手動・自動などの起点、検出理由、コンテナ、作成・開始・終了時刻、長さ、サイズ、終了コード、エラー、上限付きFFmpeg診断を保持します。時刻はUTCへ正規化したタイムゾーン付きISO 8601です。動画パスは `recordings/` からの相対パスだけを許可し、保存先外部や別録画の結果で確定することを拒否します。

V1.0.2のGUI一覧は録画と対戦記録を読み取り専用DTOへ結合し、開始日時、デッキ名、勝敗、先後、コイン、対戦種別、時間、サイズ、相手デッキ、登録元を表示します。録画IDは利用者の主要情報ではないため一覧から隠し、診断画面とCLIでは追跡用に維持します。対戦記録が未入力の場合は未入力表示とし、録画行を失いません。デッキ名列は登録カラーを小さなスウォッチとして重ね、文字列側に余白を確保して長い日本語デッキ名を省略せず表示します。コイン、対戦種別、時間、サイズ、相手デッキは列メニューで表示を切り替えられますが、相手デッキだけは既存利用者の一覧幅を変えないため初期非表示です。

各行の末尾には再生、対戦記録編集、Explorer、削除の4アイコンを固定順で表示します。アイコンにはツールチップとフォーカスを設け、`Enter`、`Ctrl+E`、`Ctrl+O`、`Delete`でも同じ操作を実行できます。ダブルクリックはUI設定で録画再生または戦績編集を選べます。既定値は従来互換の録画再生で、録画なし行や編集不可行ではボタン操作と同じ可否判定に従います。行内クリック領域は対象行を先に選択してから処理し、削除は開始日時と関連データを含む確認ダイアログを必須とします。更新・保存等の共通操作も意味が明確な場合はアイコンを使い、不慣れな記号にはツールチップを付けます。

## 録画ライフサイクル

FFmpeg開始前に `starting` を登録します。履歴登録に失敗した場合はFFmpegを開始しません。FFmpeg開始後は `recording` へ更新し、正常停止、開始失敗、異常終了を同じ録画IDの `completed` または `failed` へ確定します。最終更新を再実行しても行は増えません。

開始後の履歴更新に失敗した場合は録画を停止し、エラーとして扱います。録画ロックはすべての終了経路で解放します。DB障害を無視して録画だけを継続する動作は行いません。

## 移行とバックアップ

DBを開くたびにスキーマ版、必須テーブル、SQLiteのquick checkを確認します。アプリより新しいスキーマは変更せず拒否します。旧版DBを移行する場合はSQLiteバックアップAPIで次のファイルを先に作成します。

```text
user_data/data/db/history.vN.UTC_TIMESTAMP.UUID.backup.sqlite3
```

マイグレーションは単一の `BEGIN IMMEDIATE` トランザクションで実行します。途中で失敗した場合は元DBをロールバックし、移行前バックアップも保持します。

## CLI

```powershell
python -m master_duel_recorder_lite history list
python -m master_duel_recorder_lite history list --state failed --since 2026-08-01T00:00:00+09:00 --until 2026-09-01T00:00:00+09:00 --limit 20 --offset 0
python -m master_duel_recorder_lite history show RECORDING_ID
python -m master_duel_recorder_lite history check
```

一覧は開始時刻、未開始なら作成時刻の降順と録画IDの降順で安定して並びます。SQL条件はすべてパラメータとして渡します。存在しないIDと不整合検出は終了コード4、DB操作失敗は3です。

`history check` は次を区別して表示します。

| 種別 | 意味 |
|---|---|
| `MISSING` | DBが参照する録画ファイルがない |
| `UNTRACKED` | MKVまたはMP4がDBへ登録されていない |
| `SIZE_MISMATCH` | DBの確定サイズと実ファイルサイズが異なる |
| `INVALID_REFERENCE` | DB内の相対パスが安全な録画保存先を指さない |

診断は読み取り専用です。録画、DB行、バックアップを削除・修正しません。

## 履歴削除

GUIの録画履歴で削除を確認すると、元録画を録画保存先内の退避領域へ移動します。その後、`duel_record_tags`、`duel_record_tag_links`、`duel_record_changes`、`duel_events`、`duel_records`、`recordings`を一つのSQLiteトランザクションで削除し、成功後に退避ファイルを消去します。DB削除に失敗した場合はトランザクションを戻し、退避ファイルを元の場所へ復元します。

存在しない録画ファイルは欠損として記録しつつDB行を削除できます。絶対パス、`..`を含むパス、録画保存先外へ解決されるパスは拒否します。録画または自動監視の実行中も削除を拒否します。この操作はユーザー確認後の恒久削除で、元に戻せません。

## V0.19.0移行

v6以前からv7へ移行するときは、SQLiteバックアップ作成後、旧`recovery_artifacts`が参照する成果物を録画保存先内で検証して`.recovery-retirement`へ退避します。`recordings.output_path`と同じファイル、保存先外、絶対パス、`..`を含む参照は削除対象にしません。v7・v8移行成功後に退避成果物を削除し、失敗時はファイルを元へ戻してDBトランザクションをロールバックします。通常録画、通常履歴、失敗コード、エラー、診断は維持します。

v8の`seasons`は期間重複を許可し、`duel_records.season_id`はNULL許容です。`own_deck_id`と`opponent_deck_id`は既存文字列から移行し、文字列列も履歴表示と監査互換のため維持します。録画履歴フィルターはSQLへシーズン・両者デッキ・タグIDを渡してから`LIMIT`を適用します。異なる条件はAND、複数タグはORです。
