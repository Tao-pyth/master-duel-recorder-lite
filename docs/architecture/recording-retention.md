# 元動画の保存管理（V3.1.0）

保存管理は `recording_retention.py` の共通サービスを明示的に呼び出す。
サービスの生成・履歴参照・設定保存・バックアップ復元では新しい動画整理を開始しない。
通常GUIの起動は `startup_maintenance.py` に順序を集約する。

## 保存対象と情報の責務

自動整理の対象は recordings 領域内の登録済み元動画のみ。
容量は保護・未登録・削除の退避中を含む実ファイルサイズで計算する。
投稿用MP4、クリップ、preroll、未登録動画へ削除対象を広げない。
上限を達成できない場合は、未達と見送り理由を表示する。

対戦カードの使用・明示非使用・不明・初動は duel_id に所属する。
動画を削除しても、戦績・タグ・メモ・確認経緯・投稿URLとともに保持する。
一般マーカー、動画上のカード観測・候補は動画実体・世代に所属し、動画削除の成功確定時に除去する。
動画がないことや観測が0件であることから非使用を推定しない。

## 設定と判定

- `[storage].max_gib` は非負整数、0は無制限。1GiBは1,073,741,824 bytes。
- `[storage].retention_days` は非負整数、0は無制限。1日は86,400秒。
- `[upload].delete_source_after_upload` は初期false。

期限判定は開始日時、欠落時は作成日時をUTCへ揃える。
起動整理の現在時刻を固定し、期限より厳密に古い動画だけを対象とする。
期限を先に処理し、続いて実容量を再評価する。
古い順は日時と recording_id で安定させ、GUI一覧の1000件制限へ依存しない。
不正日時、使用中、保護、リンク・ジャンクション・共有参照、変更された動画は見送る。

## 排他と事前バックアップ

削除と管理操作は同じ data/video-operations.lock を使う。
動画利用の登録はこのロックを短時間取得してから利用leaseを保存する。
既存の利用元が生存中、または終了を確認できない場合は動画を保持する。
録画処理との交差は既存の recording.lock でも防ぐ。

DataProtectionService.retained_backup はDB・設定の検証済みバックアップを作成する。
作成した通常世代をローテーションの必須保持対象にする。
保護世代で保持枠が埋まった場合や新世代を容量内に確保できない場合は、成功を返さず削除を止める。
処理中は data-protection.lock を保持して、別の作成・世代整理による消失を防ぐ。
破壊操作の直前にもバックアップの実在とSHAを検証する。
バックアップに元動画は含めない。

## 物理削除と回復

| 段階 | 保存・操作 |
| --- | --- |
| intent | 現物サイズ・mtime・SHA、動画実体・世代、理由、バックアップ、投稿出自を先にDBへcommit |
| rename | 同じrecordings領域内の `.mdrl-video-staging/<UUID>.pending` へ移す |
| staged | 退避済みをDBへcommitし、保存値・保護・利用・現物を再確認 |
| unlink | 退避動画を削除する。ここまでは動画マーカーを消さない |
| unlinked | 物理削除成功をDBへ保存 |
| completed | 理由・日時と動画状態を確定し、対象世代の動画依存情報だけを単一transactionで除去 |

unlink前の通常障害は、同一性と元パスの空きを確認して元動画を戻し、intentを中止する。
戻せない場合は未完了journalを残して、正常完了にしない。
unlink後のDB障害は次の通常起動で記録を回復する。動画自体は復元できない。
既に確定した削除の再処理では元の理由を上書きしない。
手動の保護対象削除の確認は、その操作だけで有効とし、再起動で再利用しない。

## 通常起動と投稿後

通常GUIでは保存構造の移行、journal回復、期限、容量、永続化された投稿後再試行要求の順に確認する。
その間は新規操作とカードworkerを待機させ、画面の進捗表示を継続する。
未完了journalが残る場合は録画・動画操作を解禁せず、設定・診断へ案内する。
診断CLI、worker、version、smokeは新規整理の入口にしない。

投稿後はAPI受領成功とCOMPLETED・video ID・URLの保存再読込を確認し、最新の保存済み設定を使う。
実送信MP4のサイズ・SHA、manifest、準備キュー、元動画の内容を削除直前まで再照合する。
sourceはrecordings相対、exportはexports相対、manifestはqueue相対で出自を保存する。
削除の失敗は投稿成功を取り消さない。
一時的な開始前見送りだけを出自付き再試行要求に保存し、過去のcompleted投稿を走査しない。
投稿中の終了操作は、投稿と削除後処理が成功・見送り・失敗の終端になるまで待つ。

## 復元・JSON・完全削除

JSONに完了した投稿情報・確定削除履歴・カード正本・動画根拠を含める。
未完了journal、再試行要求、解析job/checkpoint、送信待ちは持ち出さず、実行を再生しない。
取込・復元で戻ったマーカーは動画内容と時刻基準の一致を確認するまで利用不可とする。
復元成功時だけ設定と保護表示・未保存編集の基準を同期し、復元自体から新規整理しない。
snapshotにない後発の削除理由は引き継がず、原因不明と確認不可を区別する。
完全削除・初期化・本番JSON置換は関連行を所有者別に子から親へ処理し、共通カードや他対戦へ波及させない。

これらの本番GUI・管理操作の接続とリリース検証は各Issueの完了条件で確認する。
