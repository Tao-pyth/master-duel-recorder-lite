# V3.1.0 の保存構造と旧DB移行

[W8 #686](https://github.com/Tao-pyth/master-duel-recorder-lite/issues/686)の実装設計です。schema 17/18から19への移行を、一つの事前バックアップとSQLite transactionで行います。録画ファイルは移行対象に含めません。

## 所有関係

| 保存先 | 責務 |
| --- | --- |
| `card_identities` | 対戦が参照する安定したカードID・名称。解析対象設定の削除では消さない |
| `card_target_identity_links` | `card_targets`の解析設定と安定カードIDとの対応 |
| `duel_card_information` | 対戦・カード・使用者ごとの使用／明示非使用／不明、確認元・revision |
| `duel_card_openers` | 対戦・使用者ごとの初動確認。動画マーカーへのFKを持たない |
| `duel_card_information_changes` / `duel_card_opener_changes` | 正本の確認・訂正履歴。動画がなくても成立する |
| `recording_video_assets` | 録画の各動画実体・世代・時刻基準・指紋・利用状態。現世代は録画ごとに最大1件 |
| `card_observation_links` / `duel_event_sources` | 観測・一般マーカーの動画実体と任意の使用情報への関連 |
| `card_analysis_job_sources` | 解析入力の動画実体・世代・指紋snapshot |
| `recording_video_protection` | 録画の保護。原録画の成功・失敗とは独立 |
| `video_asset_uses` | 実行時の動画利用の記録。OS排他と併用し、行の存在だけを利用終了の証拠にしない |
| `video_deletion_history` | 確定した削除理由・日時。動画世代ごとの既存原因を上書きしない |
| `video_deletion_journal` | intent・退避・unlink・DB確定にまたがる未完了操作の回復材料 |
| `upload_cleanup_requests` | 適格な投稿後見送りに対する明示的な再試行要求。過去の投稿から自動生成しない |
| `card_migration_review_items` | 自動対応できない旧情報の原文と要確認理由 |

旧`card_nonuse_confirmations`と`card_opener_confirmations`は対戦側へ移して廃止します。通常集計は対戦正本のみを参照します。既存の観測・解析job本体へ列を追加せず、動画実体の所有と正本への任意関連を専用表へ置きます。マーカーを消しても対戦正本へ削除が連鎖しません。

既存CLIの明示的な再投稿を維持するため、完了投稿の録画ID一意制約を通常の部分indexへ変更します。同じ録画の複数の完了投稿を保持し、更新日時・投稿IDの順序で最新を取得します。通常投稿の重複防止は投稿サービスで行い、この変更から自動再投稿を開始しません。

## 意味を変えない移行

- 旧対象カードのIDを初期の安定カードIDとして使い、設定と同一性を分離する。
- `confirmed`だけでは使用にしない。`supports_use=true`かつ既知の行動を持つ確認済み観測だけを使用へ移す。
- 使用者不明は不明のまま保存し、要確認へ登録する。カード未対応や矛盾は原文を要確認に残し、無断でカード・使用者を補完しない。
- 同じ対戦・カード・使用者の複数使用は正本1件へまとめ、根拠マーカーは各件を保持する。
- 非使用は明示確認だけを採用する。非使用の確認解除は不明として保存する。使用と非使用が競合する旧情報は、既存統計と同じ使用優先の正本を保ち、競合を要確認に残す。
- 初動のカードと確認状態をマーカーから先に移す。不正な初動を別カードへ割り当てず、元情報を要確認に残す。
- 確認済みの使用・明示非使用・初動がある録画に対戦がなければ、録画に対して決定的なIDのdraftを1件作る。開始日時（欠落時はcreated_at）以外の勝敗・先後・コインはunknown、デッキ・メモは空にする。候補だけではdraftを作らない。
- 旧動画の実在・内容をDBから断定しない。動画実体は世代1・`unverified`として登録し、元パス・保存サイズを保持する。利用は現物と指紋・時刻基準を照合してから許可する。

## バックアップ・失敗回復

通常の実行時入口では、DBと設定を含む検証済みのprotectedバックアップを移行前に作ります。単独DBを扱う低水準APIはSQLite backupを作成して検証します。バックアップが存在せず、または検証できなければ移行を始めません。

DDL、旧情報の読込、draft作成、正本、根拠関連、旧表廃止、schema_version/user_version更新、quick_check、foreign_key_checkを同じtransactionに含めます。途中で失敗すれば全変更をrollbackし、schema 17/18のDBと移行前バックアップを保持します。途中まで進んだschema版を正常終了として扱いません。

schema 19の再読込では移行を実行しません。旧バックアップから再移行しても、対戦・正本・救済行は同じIDになり、同じ録画へdraftが増殖しません。バックアップに動画本体は含まれません。

動画のみ削除の物理処理とマーカー消去、API橋渡し、JSON入出力・管理操作はそれぞれW3/W9/W10/W11で接続し、この保存境界を共有します。
