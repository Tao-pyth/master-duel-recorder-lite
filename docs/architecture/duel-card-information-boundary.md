# 対戦カード情報と動画マーカーの責務境界

この文書はV3.1.0へ採用した責務境界です。QA最終回答を[親Issue #672](https://github.com/Tao-pyth/master-duel-recorder-lite/issues/672)と子Issueへ反映し、schema19・API・画面・JSON・管理操作をこの境界に沿って実装します。実装・検証・正式公開の進捗は[ロードマップ](../roadmap.md)、実装設計は[使用カード分析](card-analysis.md)を参照してください。

## QAで確定した運用

- 投稿と動画自動削除の後処理が終端になるまでGUI終了を待つ。初回1を撤回し最終2を採用。
- 完了済みYouTubeの投稿URL・動画IDをJSON書き出し/取込に含める。
- カード利用マーカーをJSONに含め、同じ動画内容・時刻基準を確認して利用する。
- 確定した動画削除理由・日時をJSONに含める。
- 『動画だけ削除』と『戦績・録画履歴ごと削除』を画面の別操作にする。
- 復元snapshot内の記録を使い、後発理由を引き継がない。確認できた削除状態は『復元時削除済み』、元の原因不明は別扱い。確認不能は『確認不可』。
- 動画削除時に未確認候補とマーカーを削除し、確認済み対戦カード情報・初動を保持する。
- 投稿後削除の見送りを記録し次回通常GUI起動で再試行。最新saved設定/保護/使用中/出自を再検証する。
- 確認済みカード情報がある録画で対戦未作成ならdraft戦績を自動作成し関連付ける。勝敗等はunknown。

## 基本方針

対戦カード情報を「対戦で何を確認したか」の正本とし、動画の観測・時刻・マーカーを任意の根拠として分離します。正本は動画を持たない対戦でも作成・訂正・集計でき、根拠の削除によって結論が変わらない構造にします。

| 責務 | 所属・内容 | 寿命 |
| --- | --- | --- |
| 対戦カード情報 | 対戦ID、安定したカードID、使用者、使用・明示非使用・不明、人の確認・訂正、revision | 対戦に所属 |
| 初動の確認 | 対戦ID、使用者、カードと確認状態、独立したrevision | 対戦に所属 |
| 動画の観測・利用マーカー | 動画実体の識別、観測位置・実使用時刻・時刻の意味、行動、OCR根拠、候補・確認・却下 | 対象の動画に所属 |
| 解析ジョブ | 入力指紋、対象設定のsnapshot、解析方式・世代、進捗、checkpoint、失敗状態 | 入力動画と処理に所属 |
| カードの同一性と解析対象設定 | 安定ID・名称等と、解析対象の有効状態・別名・役割等を責務として区別 | 個別の対戦・動画の外側 |

画面でカードをタグのように付け外ししても、保存は自由記述タグと分けます。カード名の変更や解析対象の無効化は、過去の使用情報を削除・変更する理由にしません。全カード辞書の導入を意味する方針ではありません。

確認経緯は手動・解析候補の人確認・取込・移行等の種別、確認日時、revisionとして対戦側で保持します。確認履歴の保存も解析jobやマーカーの存在を必須条件にしません。解析対象設定の削除とカードの同一性の削除を分け、既存情報が参照するカードIDを失わせないようにします。

## 依存の向き

対戦カード情報を作るAPIの必須入力は対戦の情報です。録画ID、動画パス、動画時刻、マーカーID、解析ジョブID、OCR信頼度を必須条件にしません。作成・更新日時や操作の履歴は、動画上の時刻とは別の情報です。

動画側から対戦カード情報へ任意に根拠を関連付けます。使用情報1件に根拠が0件でも成立し、同じカードの複数回の利用を複数のマーカーとして関連付けられます。初動の保存・集計もマーカーのevent_idを必要としません。

マーカー・ジョブを削除する外部キーや処理から、使用情報・初動へ削除や状態変更が連鎖しないようにします。逆に使用情報を訂正しても、動画自体を削除する操作にはしません。根拠との不一致は関連解除・再確認の表示として扱います。

保存、解析、集計の間をつなぐ処理はアプリケーション側で行います。対戦カード情報の保存・集計が、動画の読込や解析workerの起動に依存する構造は避けます。

## 観測と使用の確認

未確認のOCR候補は動画側の観測です。候補を対戦側にもコピーして二つの正本にしません。カード名が表示されたこと、使用が確認されたこと、初動が確認されたことを分けます。

候補から使用情報への反映は明示的な確認操作で行います。動画を使わない手動入力・訂正やJSON取込も、同じ対戦側の規則を使います。解析jobの完了だけでは人の確認を作成・上書きしません。

- 候補0件、未解析、解析失敗、候補の却下、マーカー不存在から「非使用」を推定しません。
- 非使用は明示確認した状態です。使用者不明を自分・相手へ勝手に割り当てません。
- マーカーの「確認済み」は、その観測の確認を表します。カード表示だけの観測を確認しても、使用済みとは限りません。
- 初動は最初に観測したカードから推定せず、対戦側で独立して確認します。
- 使用と非使用、初動と使用者の矛盾は、明示的な訂正処理で整合させます。後から書かれた値を黙って優先しません。

候補確認時に使用情報も更新する操作は、一つのtransactionで関連するrevisionを確認します。古い解析世代・古い画面の保存によって、新しい対戦情報を上書きしないようにします。動画なしの手動編集には、動画側のrevisionを要求しません。

## 訂正・再解析・動画の差し替え

「時刻の修正」「根拠マーカーの削除・却下」「対戦の使用情報の訂正」は別の操作です。根拠を外すだけで、確定した使用・非使用・初動を取り消しません。

再解析は動画側の候補を更新する処理です。同じ動画実体では人が確認・訂正・却下した観測を保護し、未レビューの自動候補だけを差し替えます。対戦側で人が確認した情報を上書きしません。異なる結果は確認待ちの候補として提示します。

削除済み・差し替え済みの動画世代に対する解析結果の保存は拒否します。中断要求だけに頼らず、結果反映時にも入力世代と利用状態を検証し、遅れて完了した解析で削除済みマーカーを再作成しないようにします。

動画上の時刻は録画IDやファイルパスだけでなく、動画の実体と時刻基準に所属します。同じ録画履歴へ別動画を再関連付けした場合、古い動画の時刻や根拠を新しい動画へ持ち越しません。単なるファイル移動・名称変更と、内容差し替えを区別します。再エンコードやトリミングで時刻基準が変わる場合も、旧マーカーを自動転用しません。

対戦の使用情報は動画の再関連付けと独立して維持します。将来複数の動画を一対戦に関連付けても、使用情報を動画ごとに複製する構造にしません。この方針は複数動画機能の追加を決めるものではありません。

## 集計と画面

確認済みの使用カード・非使用・初動の集計は、対戦IDと対戦側の情報から取得します。通常集計がマーカーやevidence_jsonをJOINして使用を判定する構造は解消します。同じ対戦の同じカードに複数のマーカーがあっても、対戦数を重複加算しません。

動画の削除、解析対象の設定変更、再解析で確認済み集計は変わりません。人による対戦情報の訂正・対戦削除・snapshot復元では、その操作内容に応じて変わります。

「候補込みの参考集計」は動画の未確認観測を利用する参考表示です。動画と候補を削除した場合、参考集計の候補数は減り得ますが、確認済みの情報は維持します。候補が消えた状態は未確認であり、非使用ではありません。これは従来の「カード候補まで一律保持」からQAで変更した採用仕様です。確認済み情報の保持と候補参考の変化を、操作説明と検証へ含めます。

対戦カードの閲覧・タグ風の付与・訂正は動画の有無にかかわらず使える画面にします。動画再生・位置ジャンプ・元動画の再解析は動画側の操作として利用可能性を表示します。

## 削除・取込・復元の境界

| 操作 | 対戦カード情報・初動 | 動画観測・マーカー・解析job |
| --- | --- | --- |
| 容量・期限・投稿成功後に元動画だけ削除 | 保持 | 対象動画の観測・マーカーを削除。入力を失うjobを停止・取消し、checkpointを再開させない |
| 画面から元動画だけ削除 | 保持 | 同じ削除サービスと規則を適用 |
| 戦績を完全削除・対象を含む履歴初期化 | 対象対戦の関連情報を削除 | 対象範囲に応じて関連情報を先に処理 |
| JSON取込で対戦を置換 | 取込対象と削除対象を明示し、関連情報も一貫して処理 | 別動画の時刻やjobを誤関連付けしない |
| DBのsnapshot復元 | snapshot時点へ戻す | 動画実体・利用可能性と照合し、存在しない動画の解析やジャンプを実行しない |

共通のカード情報・設定、投稿URL等の保持・完全削除は、それぞれの所有者と管理操作の範囲に従います。対戦削除を共通カードの削除へ連鎖させません。ローカルの投稿情報を消すことと、YouTube上の動画削除は別です。

「タグのように操作する」という画面表現を、自由記述タグの初期化範囲と混同しません。対戦カード情報の削除は対戦の管理操作として定義します。

実ファイルの削除が成功する前に、マーカーを不可逆に削除しません。削除intent・同volumeへのstaging・unlink・DB確定という既存の回復方針へ、マーカー処理を含めます。unlink後にDB更新が失敗した場合は未完了として示し、journalから回復します。使用情報はこの処理の変更対象にしません。

ファイルが一時的に見えないだけで削除済みと決めません。外付けドライブ未接続や権限エラー等は利用不可として扱い、観測を直ちに消しません。確認できる削除操作・intentがある場合に、その対象の削除を完了します。復元後も動画ファイルはbackupから戻らず、根拠が利用できないことを使用情報の不存在へ変換しません。

## 移行と実装への引き継ぎ

schema18以前のcard_observationsは両方の責務を持ち、旧初動はevent_idを必須参照していました。schema19では表だけでなく、入力API、初動、統計、動画なし画面、JSON、完全削除、復元を同じ境界へ揃えます。

移行は旧使用判定（確認状態、supports_use、行動、使用者、カードの対応）と人の非使用・初動確認を読み取ります。confirmed全件を使用へ変換せず、未対応の原文・要確認理由を保持します。確認情報がある録画に対戦がない場合は決定的なIDのdraftを1件作り、勝敗・先後・コイン等を推測しません。[移行設計](retention-schema-3.1.0.md)に具体化します。

対戦カード情報をJSONの往復対象とし、動画やjobがなくても情報を復元できるようにします。旧JSONに情報がない場合は未登録として扱います。旧DB・旧backupの移行には事前backupと失敗時rollbackを設計します。snapshot後の編集・削除理由まで復元できるとは保証しません。

統合schema19と17/18からの移行は[W8 #686](https://github.com/Tao-pyth/master-duel-recorder-lite/issues/686)、正本API・編集・集計は[W9 #687](https://github.com/Tao-pyth/master-duel-recorder-lite/issues/687)、portableJSONは[W10 #688](https://github.com/Tao-pyth/master-duel-recorder-lite/issues/688)、既存DBへの取込・所有者別削除・復元同期は[W11 #689](https://github.com/Tao-pyth/master-duel-recorder-lite/issues/689)が担当します。受入条件と検証範囲は親・子Issueと採用Decide014の[Release Contract](../release-contracts/3.1.0.md)に従います。

古い動画への検索・一覧・ページ移動拡張は不採用のままです。元動画のみの自動整理、保護、手動警告、削除理由、投稿URL・既存MP4保持という既存の目的も維持します。
